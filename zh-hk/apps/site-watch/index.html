工地投訴 —— 冇訊號都記得低，有網先自動送出

地盤出事嘅位置，通常就係冇訊號嘅位置。呢個 app 當離線係常態：照樣記低，排入隊，一接返網就自己送出去。

呢個 app 仲喺開發階段，未喺 App Store 或 Google Play 上架。呢版介紹嘅係已經做好嘅部分。

最需要記錄嗰陣，通常就係做唔到嗰陣

地盤出問題嘅地方 —— 地牢、𨋢槽、未起好嘅樓層 —— 通常就係冇接收嘅地方。網頁表單會 timeout，即時上傳嘅 app 會失敗，於是件事拖到夜晚放工先做：到時細節冇咗，相由頭到尾冇影過，位置變成靠估。

工地投訴由頭到尾當離線係正常情況。投訴連相片同座標寫入本機待送清單，接返網之後 app 自己送出去，唔使有人記得要撳。

工地投訴記錄點運作

記低、排隊，然後確保佢入到去，而且只入一次。

  • 影相同座標一齊記。一宗投訴包含描述、即場影或者由相簿揀嘅相片，同埋位置。位置係必填 —— 冇位置嘅工地投訴根本冇得跟進。
  • 睇得見嘅待送清單。未送出嘅投訴會列出「等緊送出」，並寫明有網嗰陣會自動送、送之前會查重。一個你睇唔到嘅隊列，係一個你唔會信嘅隊列。
  • 防重複，兩道。每宗投訴帶一個客戶端產生嘅識別碼。一旦成功送出，個 issue number 即刻寫低，之後點重試都唔准再送。另外，開單之前會先用個識別碼查返現有列表。兩道獨立閘 —— 因為天真嘅重試最衰嗰種情況，就係回應喺半路死咗、然後同一單嘢入咗兩次，而呢樣正正會摧毀大家對共用記錄嘅信任。
  • 成隊人共用。多個人登入同一份共用記錄，一個人開嘅單，其他人都見到。

刻意冇後端

共用記錄以 GitHub 上嘅 issue 形式儲存。呢個選擇唔常見，而且係刻意嘅：即係話唔使自己養一個後端、唔使守一個資料庫、冇寄存費用，仲免費送埋完整歷史、時間戳同留言。對一隊人記錄工地問題嚟講，issue tracker 同一份投訴記錄本質上非常夾。

邊啲人啱用

記錄工地周邊問題嘅地盤團隊、安全主任同居民組織 —— 塵、噪音、阻塞、損毀 —— 一張連位置同時間嘅相，比一個電話有用好多。

儲存同私隱

投訴以 issue 形式儲存喺你喺設定階段配置嘅 GitHub 倉庫，可見範圍跟該倉庫嘅設定。相片喺上傳前於機身壓縮。憑證存放喺系統安全儲存。定位用嚟為投訴附上座標。

使用者請注意，喺工地影相有機會影到人或者私人財物，請自行妥善處理。

常見問題

冇訊號會點？投訴連相片同位置存入本機待送清單，接返網之後 app 自動送出。

會唔會入咗兩次？有兩道獨立閘。成功送出之後個 issue number 即刻寫低，之後點重試都唔准再送；開單之前亦會用客戶端識別碼查返現有列表。

啲投訴實際存喺邊？以 issue 形式存喺你喺設定階段配置嘅 GitHub 倉庫。冇獨立伺服器，而且免費得到完整歷史、時間戳同留言。

可唔可以幾個人用同一份記錄？可以。登入同一個倉庫嘅人，睇到同一批投訴。
